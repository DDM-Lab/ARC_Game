# Divergence ledger: `v1_merge_test` vs `origin/main-bugfixes`

**The question this answers:** with the LLM teammates turned off, does this branch play the
game exactly like upstream does?

**The answer today: no, and not only because of the LLM code.** We have deliberately fixed
bugs upstream still has, and at least one of those fixes changes the random-number stream,
which makes every later roll diverge. Those are good fixes. They are also, by construction,
a parity break. The point of this ledger is to name every one of them so "parity" becomes a
statement with a known exception list instead of a hope.

---

## The three versions

| # | name | LLM code | our bug fixes | expected behaviour |
|---|---|---|---|---|
| 1 | `origin/main-bugfixes` | absent | absent | the reference |
| 2 | **parity build** | present, **off** | **removed** | must equal (1) exactly |
| 3 | `v1_merge_test` (today) | present, off or on | present | differs from (1) by this ledger |

Version 2 is the load-bearing one. It isolates two questions that are otherwise tangled:

* Does merely *having* the LLM/gym code change the game when it is switched off?  → (2) vs (1)
* Do our gameplay fixes change the game?  → (3) vs (2)

Answering them separately is the only way to say something useful. A single (3) vs (1)
comparison fails immediately and tells you nothing about which cause is responsible.

## Confirmed divergences

### D1 — casework generation skips an RNG draw (**breaks the stream**)

`Map/ClientStayTracker.cs`. Upstream always rolls:

```csharp
float currentProbability = baseCaseworkProbability*Mathf.Pow(probabilityGrowthFactor, Y-1);
if (UnityEngine.Random.value < (currentProbability/100f)) { GenerateCaseworkTask(group); ... }
```

Ours wraps the whole block in `if (!facilityDeconstructing)`, so when a facility is being
deconstructed the draw is **not consumed at all**.

Why it matters more than it looks: every stochastic system in this game shares ONE global
`UnityEngine.Random` stream. A draw that happens on one build and not the other doesn't just
change that outcome — it shifts every subsequent flood, weather roll, task trigger and stay
duration. One skipped draw desynchronises the rest of the episode.

The fix itself is right (don't raise a casework request against a building being torn down).
To keep parity in version 2 it must be reverted, or restructured to roll first and discard.

### D2 — score scale (`SCORE_SCALE`)

`DailyReport/DailyReportData.cs`. Ours multiplies component scores by `SCORE_SCALE = 100f`;
upstream by `1000f`. `AddSatisfaction` clamps to [0,100], so upstream pushes up to 200 points
into a field capped at 100 — the metric pins at 100 and then collapses. Ours is correct.
Version 2 must restore `1000f` to match.

### D3 — day-start baseline seeding (bug B34)

`DailyReport/DailyReportUI.cs`. Ours seeds the report baseline with
`GetDayStartSatisfaction() * 10f`; upstream seeds it raw while rendering `/1000`, so the
reported day change is wrong by 10x. Ours is correct. Version 2 must drop the `* 10f`.

### D4 — round-end ordering — **WITHDRAWN, not a divergence**

Originally recorded as "upstream leaves `//OnRoundEnd?.Invoke();` commented out while ours
calls `SafeInvokeStatic(OnRoundEnd)`". That was true of upstream *before* merge `e85fe2c9`, and
it is the state this ledger was written against. It is no longer true. At `e85fe2c9` upstream
has, at both call sites:

```csharp
//OnRoundEnd?.Invoke();
SafeInvokeStatic(OnRoundEnd);
```

Both branches invoke the handler, at the same point — after round-end finalisation, before
`AdvanceTimeSegment()`. The commented line is a leftover, not the live code. Nothing to revert
in version 2.

Recording the withdrawal rather than deleting the entry, because the mistake is instructive:
this was catalogued from a diff read at one commit and then treated as standing fact across a
merge that resolved it.

### D5 — confirm-time validation

`Tasks/TaskDetailUI.cs`, the largest single file divergence (87 modified hunks). Ours routes
all three confirm paths through `ValidateBeforeConfirm`, which additionally checks delivery
feasibility, worker assignment and budget (`WouldAllowSpend`). Upstream inlines a smaller set
at two of the three call sites. Effect on parity depends on whether a rejected confirm is
reachable in an unattended scripted episode — under the default `allowNegativeBudget = true`
the budget arm is inert, so this may be benign in practice. **Needs the harness to settle.**

### D6 — external-relation scheduling: ours caps, upstream does nothing

`ScenarioLoader/GameConfigLoader.cs` and `Tasks/TaskSystem.cs`. Two halves, and the more
alarming half turned out to be inert.

**Upstream's scheme does not run.** It declares `budgetAdvisoryER` / `budgetEmergencyER` and
calls `ApplyInitExternalRelationFrequency()`, which splits the frequency into two day-intervals
and decides which trigger gets which by

```csharp
bool advisoryGetsLower = new System.Random().Next(0, 2) == 0;
```

But the method opens with `if (budgetAdvisoryER == null && budgetEmergencyER == null) return;`
and **both fields are `{fileID: 0}` — null — in every scene that ships** (MainScene and
TutorialScene, checked directly in the serialized YAML). So the split never happens and the
clock-seeded coin is never flipped.

This retracts the strongest claim the ledger made. It previously said "`main-bugfixes` cannot
reproduce its own seeded episodes" and "byte-identical trajectories are not achievable in
principle" because of that unseeded generator. Neither holds: the generator is unreachable.
Upstream's seeded episodes are reproducible, and there is no seeding work owed to it on this
account. The code is dead, not dangerous — worth deleting upstream, not worth a fix.

**Our half is live.** Commit `a72a35a9` removed the fields and the split and enforces the
frequency as a TOTAL COUNT instead: `numExternalRelationTasks` (`TaskSystem.cs:580`) with a
`continue` that skips any external-relation contact once the count is reached. Upstream has no
such cap and, with its own scheme dead, places no limit on these tasks at all. So ours generates
strictly fewer external-relation tasks, which changes how many draws come off the shared Random
stream. Version 2 removes the cap.

### D7 — the parameter sheet reaches the game on our build and not upstream's

`GameDataManager.cs`. Upstream's `Awake` calls `StartCoroutine(LoadAllData())` and
`LoadAllData` immediately tests `if (useExternalConfig && configLoader != null)`. In MainScene
the `configLoader` reference is not wired, so upstream takes the `else` branch and runs on
**hardcoded defaults**. Ours adds one line before the coroutine starts:

```csharp
// A scene whose GameDataManager has no loader wired (MainScene) used to fall straight to
// SetDefaults(); find the loader that is in the scene instead (BUG_REPORTS A9).
if (configLoader == null) configLoader = FindObjectOfType<GameConfigLoader>();
```

so ours waits for the loader and runs on **the parameter sheet**.

Caught by the harness, not by reading the diff. Two seeded headless runs produced:

```
upstream   GameDataManager: External config disabled or missing loader. Using Hardcoded Defaults.
           SatisfactionAndBudget initialized from DataManager - Budget: 10000, Sat: 50
ours       GameDataManager: parameters in effect {"source":"https://docs.google.com/...",
           "budget":8000,"satisfaction":0,"days":8, ...}
```

This is the single largest divergence in the ledger by consequence: **every number in the game
comes from a different place.** It is also a fix we want — a sheet nobody reads is a sheet that
lies. But it means a (3) vs (1) comparison can never show parity, and version 2 must revert the
auto-find so both builds start from the same values.

Two follow-ups this exposes and does not settle:

* **The parameters reach `GameDataManager` and never reach the game.** Across a full 18-round,
  4-day hermetic episode the probe recorded `budget = 10000` on every single line, and
  satisfaction opening at 50, while the very same run logged
  `parameters in effect {"budget":8000,"satisfaction":100,...}`. `SatisfactionAndBudget` has
  already initialised from the pre-load defaults by the time the parameter file lands, and
  nothing re-applies them. So D7's fix is only half a fix: the sheet is *read*, and the economy
  it is supposed to configure still runs on hardcoded numbers. This is a bug in its own right,
  it is not a parity question, and it is probably the most consequential single line in this
  document for anyone running experiments off that sheet.
* `GameDataManager.SetDefaults()` may not be identical on the two branches (the ledger already
  flags `loadedInitialKitchenFoodCapacity` / `loadedInitialShelterFoodCapacity` as ours-only).
  Version 2 must diff the two default sets directly, not assume them equal.

### D8 — headless mode forced the LLM path on (fixed)

`WebSocketManager.Start()` had `if (Application.isBatchMode) { enableWebSocket = true; ... }`
with no escape, so a headless run could not be made to play without the router attached. The
first parity run of our build connected to a live router on `:9876` while pretending to be a
teammates-off control.

Fixed here: `-no-llm` / `ARC_NO_LLM=1` / `?llm=0`, checked in `Start()` and again in
`ConnectToServer()` so no other caller can re-attach it. This is the switch the user's
requirement — "the LLMs can be turned off and the game behaves exactly like main-bugfixes" —
actually needs to exist for the claim to be testable at all.

### D9 — the two builds load different maps, and the map is not a property of the commit

`GameConfigLoader.mapConfigServerUrl` is a **serialized scene field**, and the branches' MainScene
disagree: upstream points at `http://localhost:8765/config`, ours is blank. With a map server
running on the machine, upstream downloaded a map and applied it over the scene (67 objects: 47
forests, 27 abandoned sites, 4 vehicles, ground bounds 28x20) while ours kept the built-in layout
(15 sites, 3 vehicles, 31x22). Different geography means different flood spread, different task
sites and different draw counts, so the RNG streams cannot agree whatever the game code does.

The obvious lever does not work. Both branches *look* overridable through
`StreamingAssets/config.json`, but both read it as

```csharp
string configPath = Application.streamingAssetsPath + "/config.json";
using (UnityWebRequest cfgReq = UnityWebRequest.Get(configPath))   // no file:// scheme
```

which fails on a macOS standalone build — the same failure visible for the local parameter CSV
("WebRequest failed: Cannot connect to destination host | Path: /Users/.../game_param_config.csv").
So on desktop the scene value always wins and config.json is decorative. That is a bug in its own
right, and it is worth knowing before anyone tries to configure a desktop build by editing it.

Two things make this worse than a settings difference. It is **network-dependent**: the same two
builds compared on a machine with nothing on :8765 would have agreed, and nothing in the trace
would have said which happened. And upstream's map is **not a property of its commit** — re-run
the same binary tomorrow against a changed server and you get a different episode.

Since neither config.json nor the scene (LFS-tracked, merges whole-file) is a usable lever, the
harness sets the field at runtime: `ParityEnv` blanks `mapConfigServerUrl` under
`-parity-hermetic`, in the `AfterSceneLoad` window that lands after every `Awake` and before the
`Start()` that reads it. Both builds then run the built-in layout and download nothing.

### D10 — headless auto-confirms every confirmation popup; upstream shows it

`UI/ConfirmationPopup.ShowPopup`. Ours opens with:

```csharp
if (Application.isBatchMode) { onConfirm?.Invoke(); return; }
```

Upstream has no such branch and puts the modal on screen. So in headless every
confirmation-gated action — construction, deconstruction, first-time tutorial prompts, and the
end-of-day "go to the daily report?" prompt — runs **immediately** on our build and **waits for
a click that never comes** on upstream's.

This is why the first unattended episode died at day 1 segment 4 on both builds for different
reasons, and it means an automated driver has to handle both worlds. `ParityDriver` now clicks
the popup's confirm button when one is visible, which is a no-op on our build and the only way
forward on upstream's. The divergence itself stays in the ledger: the callback fires at a
different point in the frame on the two builds, and version 2 must decide whether to keep the
auto-accept (it is what makes headless runs possible at all) or gate it behind an explicit flag.

### D11 — `SetDefaults()` assigns the emergency frequency to the wrong field upstream

`GameDataManager.SetDefaults()`, found by diffing the two default sets directly:

```diff
-        InitialExternalRelationFrequency = defaultEmergencyTaskFrequency;
+        InitialEmergencyTaskFrequency    = defaultEmergencyTaskFrequency;   // BUG_REPORTS A9
```

Upstream overwrites the external-relation frequency with the emergency value and leaves
`InitialEmergencyTaskFrequency` at its field initialiser. Ours also sets two capacities upstream
never sets at all (`InitialKitchenFoodCapacity`, `InitialShelterFoodCapacity`).

Why this one matters out of proportion to its size: **these defaults are the values upstream
actually plays on**, because of D7 — upstream never reads the sheet, so `SetDefaults()` is not a
fallback there, it is the game's parameters. A wrong task frequency changes how many tasks are
generated, which changes how many draws are taken, which desynchronises the RNG stream exactly
like D1. Version 2 must revert this too, or D7 alone will not buy parity.

### D12 — "AI off" used to imply "gym server on" (fixed)

`GymServerManager` auto-enables the gym control socket in batch mode when
`WebSocketManager.enableWebSocket` is false. Adding the `-no-llm` switch (D8) sets exactly that
flag, so the first hermetic run would have silently started an RL server instead of playing
solo. Now guarded: with `-no-llm` and no explicit `-gym-server`, the gym server stays off.

Worth stating as a general shape rather than a one-off: in this codebase "headless" has
accumulated several meanings — no graphics, gym-controlled, auto-confirming, LLM-attached — and
they are wired to each other by inference rather than by flags. Every one of those inferences is
a place where a control condition can quietly become a treatment condition.

## What the harness has actually established

The first end-to-end run reported "RNG diverges at day 1 segment 1", which looks exactly like
D1. It was not D1. It was D7, D8 and D9 stacked: different parameter sources, a live router
attached to one side, and different maps. The harness's first real output was to catch its own
environment being non-hermetic — and it only caught it because the logs were read by hand. The
diff itself happily produced a confident wrong answer.

Since then the conditions are pinned (`-parity-hermetic`, `-no-llm`) and recorded in every
trace line, and `diff_traces.py` refuses rather than guesses. Two guard bugs were found by
testing the guard against its own target case, which is the only way this kind of check earns
trust:

* the first map fingerprint counted scene ROOT objects and reported **21 for both** a built-in
  layout and a downloaded 67-object map, because the applier parents everything under existing
  objects. Counting every Transform separates them (1522 vs 1570 on the same build and seed).
* that count also grows during play, so it is frozen once startup settles and excluded from the
  within-episode drift check — otherwise every run would look like a configuration change.

## RESULT: exact parity, 32/32 seeds

`-no-llm -parity-hermetic -parity-play`, seeds 1-32, 24 rounds each, the ported greedy baseline
acting (263 confirms across the suite):

```
RNG bit-exact for the WHOLE episode : 32/32 seeds
  per-seed matching-round rate      : min 100%  median 100%  max 100%

budget        exact on 32/32 seeds; worst abs diff 0.0000
satisfaction  exact on 32/32 seeds; worst abs diff 0.0000
efficiency    exact on 32/32 seeds; worst abs diff 0.0000
facilities    exact on 32/32 seeds
```

**A build containing the LLM layer, the gym server, the snapshot/checkpoint system and all the
instrumentation, with the teammates switched off, plays byte-identically to main-bugfixes across
32 seeded episodes in which a policy is actually acting.** Not "close enough" — identical RNG
cursor and identical state at every one of the 26 recorded rounds, on every seed.

That answers the question the thrust was set up to answer: **the AI-teammate code is
behaviourally inert when it is off.** Every divergence that had to be removed to demonstrate it
is catalogued below, and every one of them is a deliberate bug fix of ours or a difference in
upstream, not contamination from the agent layer.

### What it took

| reverted | what it was |
|---|---|
| D1, D2, D3, D11, D13, D17, D22 | bug fixes of ours that change behaviour |
| D6, D10, D14, D15, D16, D18, D21 | design changes of ours |
| D7, D20 | the parameter sheet reaching the game at all |
| D23 | an event subscribed to a different clock signal |
| D24 | deterministic ordering imposed on HashSet-derived lists |
| D4 | nothing — withdrawn, not a divergence |

### How it was found, for the record

The last three took a method rather than reading: pick the seed that isolates ONE half of the
problem, diff that single round's log against upstream's, then sweep for the general shape.

* **D22** came from seed 4 — identical RNG and budget for the whole episode, satisfaction
  drifting. Same draws, different logic.
* **D24** came from seed 8 — the exact inverse: state never diverged, RNG did. Same outcomes,
  different draws.

Two complementary seeds, each isolating one half, then a sweep (commented-out calls for D22,
imposed orderings for D24) to catch the sibling sites. Four blind reverts before that moved
nothing; the instrumented diff moved everything.

### What this result does NOT cover

* **Construction and deconstruction are still never exercised.** The policy confirms task
  choices; it cannot build or tear down. So **D1 remains unreachable** — the very divergence this
  ledger opens with has not been tested, only reverted. Upstream's `execute_action` reaches those
  paths and is the way to close it.
* One policy (greedy), one episode length (24 rounds), one map, one parameter set.
* Parity is demonstrated between **version 2 and version 3**. Version 4 — the shipping branch —
  still cannot be compared at all, by D7.

**This is a no-action episode.** `facilities` is empty for all 18 rounds because the driver only
advances the clock; nothing is ever built, deconstructed or confirmed. Parity here is necessary
but weak, and D1 (needs a deconstruction) and D5 (needs a confirm) are unreachable by
construction. A scripted action sequence is what would make the result strong.

Progression, for a sense of what each revert bought:

```
start          rng d1 s1   state d1 s1
after D16      rng d3 s2   state d1 s1
after D17      rng d3 s2   state d4 s0
after D20      rng d3 s2   state d2 s2 (gap now ~2 points, was ~200)
```

The one outstanding cause is D19, and it is deterministic rather than stochastic — the RNG gap
at d3 s2 is downstream of a task set that has differed since the first generation pass.

**Version 3 vs version 1, for the record:**

```
upstream   params 10000/50/8   stable
ours       params 0/0/0 -> 8000/100/8   changes DURING the episode
           => REFUSING TO COMPARE
```

That refusal is the result, not a failure to get one. **(3) vs (1) is demonstrably
non-comparable**, for a named reason rather than a suspected one, and no amount of harness work
will change that: it needs version 2.

An earlier draft of this section reported that upstream passed through a `segment 5` that ours
did not, and floated it as an unexplained mechanic divergence. It was not one — it was the
driver spending a click on a modal and an execute in the same tick, which only happened on
upstream because ours auto-confirms in batch mode (D10). Once the driver was fixed to take one
action per tick and to count observed rounds rather than clicks, the sequences became identical.
Worth keeping in the record: the first two "findings" this harness produced were both about the
harness.

What the harness now does reliably: builds and runs on both branches, drives unattended
multi-day episodes through the day-boundary modals, records an RNG checksum plus economy and
facility state per round, and refuses to compare runs that were not the same experiment.

### D13 — `AddSatisfaction` clamps on our build, not upstream's

`SatisfactionAndBudget.AddSatisfaction`. Ours: `Mathf.Clamp(currentSatisfaction + amount, 0, 100)`.
Upstream: `currentSatisfaction += amount;`.

This is the mechanism behind the 313.33 the harness keeps reporting for upstream on a 0-100
field. D2 explains why a delta that large is generated; D13 explains why nothing stops it. The
two travel together and both must be reverted for version 2, which is how the reverted build
moved from 100 (pinned at our clamp) to 250 (running free, like upstream).

### D14 — food-request probability comes from the sheet on our build

`Tasks/TaskDatabases.CheckProbability`. Ours replaces the asset's own probability trigger with
`Random.Range(0f, 1f) < gdm.InitialFoodDemandFrequency` for any task whose id contains
"FoodRequest"; upstream calls `trigger.CheckCondition()`. Same position in the stream, different
distribution, so any run that reads a sheet diverges from the first food-request evaluation.

Recorded here with a correction attached: this was briefly written up as the cause of version
2's first RNG divergence. It was not. The draws in question came from `TaskTrigger.CheckCondition`,
which both branches share, and our override never fired in that run because `SetDefaults` leaves
`InitialFoodDemandFrequency` negative. Reverted because it is a real divergence under a sheet-
driven run, not because it explained this one.

### D15 — task-generation schedule: different passes on different segments

`Tasks/TaskSystem`. Two changes at once:

| | upstream | ours |
|---|---|---|
| gate | `newSegment != 3` -> segments 0, 1, 2, **4** | `newSegment < roundsPerDay - 1` -> segments 0, 1, 2 |
| day start | none | extra `OnDayStarted += OnDayStarted` pass |

Reverting the gate is straightforward. The day-start half is not: ours moved the segment-0 pass
onto `OnDayStarted`, which does not fire for day 1, and after reverting the subscription **day 1
still runs no segment-0 pass on our build** — the `OnTimeSegmentChanged` event never arrives for
segment 0 of day 1 here, while it does upstream.

The consequence is large and visible in the logs. Upstream's day 1:

```
segment 0  ->  3 triggered task-facility combinations  (Budget_Allocation,
                 two Community_TransportRequest)
segment 1  ->  2  (Community_TransportRequest, Worker_TooMany_Idle alert)
segment 2  ->  3
```

Ours, same seed, same parameters, same map:

```
segment 1  ->  0        segment 2  ->  0        segment 4  ->  0
```

**Upstream's first day generates tasks and ours generates none.** Different tasks means
different trigger evaluations means a different number of draws off the shared stream, which is
the RNG divergence the diff reports at day 1 segment 1. The remaining cause is in `GlobalClock`'s
day-1 opening sequence — our "A1 clock fix" — and that is the next revert.


### D16 — day 1 is a normal day on our build and a scripted animation upstream

`GlobalClock`. Upstream branches at `currentDay == 1 && currentTimeSegment == 0` into
`Day1SkipCoroutine`, which steps all four rounds through a clock animation: it assigns
`currentTimeSegment` directly, **never raises `OnTimeSegmentChanged`**, and fires only
`OnRoundEnd`. Our fix (BUG_REPORTS C.10) removed the coroutine so day 1 is a normal day for
humans as it already was for the gym — "one rule for humans and agents".

The consequence is total. Upstream's day 1 runs **no** generation, consumption, ageing or
delivery ticks and takes **no draws at all**: its RNG cursor is frozen for the entire first day
while ours advances. This was the single largest behavioural divergence in the ledger, and
restoring the coroutine moved the first RNG divergence from **day 1 segment 1 to day 3
segment 2** in one step.

### D17 — worker-use satisfaction normalised against a different denominator

`DailyReport/DailyReportData.S_WorkerUse()`:

```diff
-        float denom = assumedTotalWorkerPoolSize * roundsElapsed;     // upstream
+        float denom = Mathf.Max(1, d.GetCumulativeWorkerPoolRounds()); // ours, BUG_REPORTS B23
```

Ours normalises by the live pool-rounds the class already accumulates; upstream by a fixed
assumed headcount, so with a pool below that size the ratios span a sliver of their range and
above it they exceed 1. Ours is right. The visible effect is that upstream records a
`Worker use progress +63.3` on day 1 that our build does not record at all.

Reverting it moved the first STATE divergence from **day 1 segment 1 to day 4 segment 0**.

### D18 — community food depletion reads a different chance, and had an extra pass

`Tasks/CommunityFoodDepletionManager`. Two differences, both reverted:

* upstream reads `GameConfigLoader.GetInitialFoodDemandFrequency()` synchronously in `Start`;
  ours waits on a coroutine for `GameDataManager.InitialFoodDemandFrequency` so the sheet wins.
  A different depletion chance is not just a different outcome: a depletion hit spawns a
  food-request task, which changes how many tasks exist to evaluate on later rounds.
* ours also subscribed to `OnDayStarted` (an extra depletion pass per day, one draw per
  community), which existed only because the A1 clock fix moved the segment-0 tick there.

Reverted for correctness; it did **not** move the divergence, so it was not the cause of
anything currently outstanding.

### D19 — `Community_TransportRequest` never triggers on our build (**cause: D20**)

On the first generation pass of the run, with identical RNG cursors and an identical facility
scan, upstream triggers two relocation requests and ours triggers none.

Four blind reverts failed to move it. What settled it was a temporary diagnostic in
`AreTriggersActivatedForFacility`, printing each trigger's verdict for this one task:

```
[D19] Community_TransportRequest @ Community01 prob=0.5 -> True   results=[True,False,True]
[D19] Community_TransportRequest @ Community03 prob=0.5 -> True   results=[True,False,True]
[D19] Community_TransportRequest @ Community02 prob=0.5 -> False  results=[True,False,False]
```

The **probability roll matches upstream exactly** — 01 and 03 hit, 02 misses, precisely the two
upstream generates. The stream was never the problem. `requireAllTriggers` is true and the
MIDDLE trigger, the resource trigger, is false on our build. One more diagnostic named the
number:

```
[D19res] Community01 type=Population cond=MoreThan thr=200 -> False  amount=40 cap=400
```

The lesson is worth keeping: four rebuilds were spent reverting plausible-looking code against a
matching RNG cursor, when one `Debug.Log` in our own build would have answered it immediately.
A matching cursor means the same draws were taken; it says nothing about what was done with them.

### D20 — the sheet overwrites prebuilt stock; upstream keeps the prefab's

`Delivery/BuildingResourceStorage.ApplyConfiguredCapacities` (BUG_REPORTS B35), a method with no
upstream counterpart. For a community it does:

```csharp
int residents = gdm.InitialResidentsPerCommunityNumber;   // 40 from SetDefaults
currentResources[ResourceType.Population] = residents;    // prefab authored 400
```

Both builds log `Community01 storage initialized to 400 of Population` at startup; ours then
silently replaces 400 with 40. `Community_TransportRequest` requires `Population > 200`, so on
our build that task can never fire at all.

This is D7's consequence rather than an independent choice — upstream ignores the sheet, so
"apply the sheet" has no upstream behaviour to match — but it is the sharpest illustration of
what D7 costs: one parameter, applied where upstream applies nothing, silenced an entire task
type for the whole game.

Disabled in version 2. Relocation requests now fire (12 against upstream's 13).


### D21 — the daily budget grant differs, and it compounds (**found only under play**)

`Tasks/TaskSystem.ApplyConfiguredAllocation` — 2 call sites on our branch, **0 upstream**. It
rewrites the Daily Budget Allocation task's budget impact with the sheet's
`InitialDailyBudgetAddition` instead of using the value authored on the task asset.

Every day the policy confirms that task, upstream grants **+5000** and ours grants **+3000**:

```
seed 1        upstream   ours
(2,1)           15000    13000
(3,1)           20000    16000
(4,1)           25000    19000     ... and so on, every day, for the whole episode
```

Across 32 seeded, played episodes: **budget agreed on 0 of 32 seeds**, median worst gap
292,000, largest 592,000, smallest 8,000 — against a starting budget of 10,000. This is not a
rounding difference; the two builds are running different economies.

**It was invisible for the entire investigation up to this point.** Eighteen rounds of
clock-only comparison reported budget as *exactly* equal on every round, because nothing was
ever spent or granted. The divergence needs someone to confirm the funding task, and the
harness had no one doing that. Every parity number reported before the policy existed should be
read with that in mind.

Same family as D7 and D20: the sheet drives our build where an asset or prefab drives upstream's.
Three separate instances now — community population, prebuilt capacities, and the budget grant —
which makes it less a collection of bugs than a single unresolved question about where the
game's numbers are supposed to come from.


### Anatomy of the 32-seed divergence — two roots, not twenty

Having the suite made it possible to ask *why* the two builds disagree rather than merely how
much. Every divergence measured across 32 played episodes traces to one of two roots, and
neither is an arithmetic difference — `S_Lodging`, `S_Casework` and the whole `Recalc*` family
are byte-identical between the branches once D2 and D17 are reverted. **The scoring code agrees;
its inputs do not.**

**Root 1 — the budget grant (D21).** Direct and systematic: +5000 upstream, +3000 ours, every
day the funding task is confirmed. Present on 32/32 seeds, final gap median 292,000.

**Root 2 — the two builds hold different task sets.** This is the D19/D20 family, and it
surfaces in the score two different ways:

| | seeds | size at episode end | mechanism |
|---|---|---|---|
| small | 24/32 | median 3, max 4 | `Task Incomplete Penalty`, -1 per expired task |
| large | 8/32 | ~±200, sign varies | a `Lodging progress` step that fires on one build and not the other |

Both mechanisms are **shared code**. The Task Incomplete Penalty exists on both branches (two
call sites each); it simply fires nine times on one build and zero on the other, because
different tasks are outstanding to expire. Likewise the ±200 is a single lodging-score step that
lands when housed population crosses a threshold — reached on one build and not the other,
sometimes in opposite directions, which is why the sign varies.

Three of the eleven seeds with a large mid-episode gap converge again by the end, so that
population is part timing and part permanent. The small population never converges: -1 per
expired task accumulates monotonically.

The practical consequence for anyone reading the numbers: **there is no separate "score bug" to
find.** Fix what tasks get generated and confirmed, and the score follows. The remaining work is
D21 and the task-set question, not the scoring pipeline.

**Tested, and the prediction was wrong in an instructive way.** Reverting D21 and re-running all
32 seeds should, on the analysis above, have made budget exact. It did not: budget went from
exact on 0/32 seeds to exact on only 6/32, and the median worst gap *rose* slightly (292,000 to
300,000).

The systematic half did close — the daily grant now matches round for round, +5000 on both,
through day 3. What remains is root 2 showing up in the BUDGET rather than only in the score,
which the analysis had quietly assumed it would not: the two builds generate a repeatable
+100,000 funding task a different number of times (9 against 6 on seed 2), and which build comes
out ahead varies by seed. See F1.

So the two roots stand, but "root 2 affects satisfaction" was too narrow — root 2 affects every
downstream number, and in budget its effect is larger than root 1's ever was.


### F1 — a repeatable +100,000 funding task (a game-balance finding, not a parity one)

Found by accident, and the most consequential thing in this document for anyone running RL.

`Budget_Advisory.asset` ("Storm Funding Advisory", `taskOfficer: ExternalRelationship`) grants
**+100,000** and regenerates. The greedy baseline confirms it every time it appears — of course
it does, it maximises budget — and in a five-day episode the budget goes:

```
10,000  ->  930,000
```

That is a money pump. Any agent that notices it has effectively unlimited budget, every
cost-based term in the reward stops constraining anything, and the benchmark's cost-efficiency
metrics measure nothing. It is exactly the shape of reward hacking an RL run will find without
being told to look.

**Our shipping branch already mitigates it and upstream does not.** The D6 cap
(`numExternalRelationTasks`, default 3 from the sheet) applies to external-relation contacts,
and `Budget_Advisory` is one — so our build stops issuing them after the cap while upstream
issues them indefinitely. That reframes D6: it is not only a reinterpretation of what
"frequency" means, it is the only thing standing between this task and an unbounded budget.

Version 2 has the cap removed for parity, which is why the exploit is visible in the suite at
all: 9 grants on version 2 against upstream's 6 for the same seed.

Worth deciding deliberately rather than leaving as a side effect of D6: should this task repeat,
and if so should the grant be that large?


### D22 — expired tasks cost us satisfaction and cost upstream nothing

`Tasks/TaskSystem`, at **two** sites — `ExpireTask` and `SetTaskIncomplete`. Upstream has the
call commented out in both:

```csharp
//ApplyTaskPenalties(task);
```

We re-enabled it. So every task that expires unfulfilled charges us its satisfaction impact and
charges upstream nothing.

Isolated on seed 4 of the suite, which is the cleanest case the harness has produced: **identical
RNG cursor and identical budget for all 26 rounds**, with satisfaction dipping 1-3 points on our
build during segments 2-4 of each day and recovering to exactly upstream's value at each day
start (the daily report recomputes from cumulative state, which wipes the transient). Same draws,
same money, different score — a pure logic difference with the stochastic half held fixed.

This is the mechanism behind the small population in the divergence anatomy: 24 of 32 seeds
ending within 4 points, accumulating -1 per expired task. The earlier note that the penalty
"exists on both branches, it simply fires on one" was half right — the *method* exists on both;
the *call* does not.

Found by a systematic sweep rather than by reading: every line in upstream matching a
commented-out call, checked against whether the same call is live on ours. 53 candidates, 52 of
which were old signatures with live replacements beside them (upstream charges construction at
`BuildingSystem.cs:219`, not the commented `:206`). D22 was the one real hit, and the sweep is
worth keeping as a one-off check because this class of divergence is invisible in a structural
diff -- the line is *present* on both sides.

**The design question:** should an unfulfilled task carry a satisfaction penalty? Upstream says
no, we say yes, and neither is obviously wrong. It matters more than its size suggests, because
it is the only pressure in the game against letting tasks lapse.


### D23 — the daily report is generated on the wrong side of a round boundary

`Tasks/WeatherReportSystem`, a two-line divergence with no arithmetic in it at all:

```csharp
GlobalClock.Instance.OnTimeSegmentChanged += OnTimeSegmentChanged;   // upstream
GlobalClock.Instance.OnDayChanged        += OnDayChangedReport;      // ours
```

`OnDayChanged` fires BEFORE `OnTimeSegmentChanged(0)` at the rollover, so our build opens the
daily weather and disaster report one tick earlier than upstream's. Visible in the logs as
nothing more than a reordered line:

```
upstream   New day weather  ->  segment-0 tick  ->  daily weather & disaster report
ours       New day weather  ->  daily weather & disaster report  ->  segment-0 tick
```

Why it matters out of all proportion to its size: the probe samples at segment boundaries, so
the same draws taken on the other side of a boundary read as a **different RNG state at (2,1)**
on seeds where nothing else differs at all. Every technique used up to this point was blind to
it — both files compute identically, the diff of the mechanic is empty, and the only trace of it
is a phase shift.

Found by taking the single seed whose RNG diverged earliest and diffing the events of that one
round against upstream's, rather than by reading code.

### The +/-200 lodging step is phase, not mechanism

The large satisfaction population (11 of 32 seeds at roughly +/-200, sign varying) had been
recorded as a distinct mechanism. It is not. Both builds apply exactly one
`-200.0 - Lodging progress` step; they apply it at different times:

```
seed 1   upstream  log line 7232
         ours      log line 5178
```

`S_Lodging()` crosses its threshold when relocation tasks resolve or expire, which happens on
different rounds because the task sets differ. Seeds where both builds reach the step inside the
24-round window converge; seeds where only one reaches it end ~200 apart, with the sign
depending on which got there first.

So the anatomy simplifies again. After D22 and D23 there is **one** remaining root: the two
builds hold different task sets at different times. Budget (via F1's repeating funding task),
satisfaction (via the lodging step) and the RNG cursor are all expressions of it.


### D24 — we impose a deterministic order on HashSet-derived lists; upstream does not

`Flood/FloodSystem` (three sites) and `Delivery/DeliverySystem` (one). Wherever a `HashSet` is
turned into a `List` that `Random.Range` then indexes into, our branch sorts it first:

```csharp
expansionCandidates = new List<Vector3Int>(new HashSet<Vector3Int>(expansionCandidates));
expansionCandidates.Sort(...);      // ours only
```

Our sort is **correct** and the comment beside it explains exactly why: HashSet enumeration order
depends on internal layout, so an identical candidate SET can still expand different tiles, and
that is what made a restored game diverge from a replayed one. It is a real determinism fix.

It is also the last parity break. Same set, same draw, same index -- **different tile**, because
the list is in a different order. Visible in the logs as two builds expanding the flood from an
identical 97 tiles under identical weather and picking overlapping-but-different targets:

```
upstream  added (-14,-6) (8,-7) (0,-1) (-6,-1) (8,5)   -> 49 tiles
ours      added (-14, 5) (9,-8) (0,-1) (-6,-1) (8,1)   -> 50 tiles
```

Two of the five agree; three do not. From there every later flood decision differs, and with it
the whole stream.

Found by taking the seed whose state NEVER diverged but whose RNG did -- the inverse of the seed
that isolated D22 -- and diffing that one round. Four sites, all the same shape, found by
sweeping for orderings present on our side and absent upstream.

**Result: with D24 reverted, seed 8 reports `PARITY HOLDS across every compared round: identical
RNG cursor and state` over 26 rounds of played episode.** The first time the harness has printed
that line.

## RNG neutrality: the assumption instrumentation rests on

75 hunks are `SnapshotDebug.Mark` calls and similar. These are believed behaviour-neutral
because they only record a label. That belief is load-bearing for version 2 and should be
mechanically checked rather than trusted: a single `Random.value` inside an instrumentation
path — or a `Debug.Log` that formats a value by calling something with a side effect — would
desynchronise the stream exactly like D1 does.

`SnapshotDebug.Mark` is compiled in on our build and absent upstream, so version 2 keeps it
(it is how the harness observes anything at all) and the harness must demonstrate that
running with marks produces the same trajectory as running without.

## What is NOT yet established

* Whether the 261 "modifies existing" hunks contain further behavioural changes beyond
  D1–D5. They were classified structurally, not read line by line. The harness is the
  efficient way to find the rest: a behavioural diff localises them without anyone reading
  11,000 lines.
* Whether every LLM-only file is genuinely inert with the LLM path off.
* Whether `GameConfigLoader.cs` changes any parameter default beyond D6. A changed default
  would move every number in the game and would not look like a mechanic change in a diff.
  Two new fields (`loadedInitialKitchenFoodCapacity = 200`,
  `loadedInitialShelterFoodCapacity = 100`) were added on our side and need checking against
  the prefab values upstream uses implicitly.

## Recommended resolution

D6 deserves its own decision: seeding that coin flip is a fix upstream needs for its own
sake, since without it `main-bugfixes` cannot reproduce a seeded episode. It is also the one
divergence that no harness can paper over.

Upstreaming D2, D3 and D4 would shrink this ledger toward empty and make parity a real
invariant rather than a managed exception list — they are fixes upstream wants anyway. D1 is
the one that must be handled carefully either way, because the RNG-ordering consequence is
easy to reintroduce by accident and invisible in review.
