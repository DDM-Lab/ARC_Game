Three wings, one contract, one game

How the live human-AI game, the benchmark harness, and the RL trainer share a single action contract and one game engine — and how people, models, and run-data move between them.

01 — The shape

Three wings drive the same engine through the same contract

Each wing is a different driver of the ARC disaster-response game: humans-plus-officers (live), scripted evaluation (benchmark), and a training loop (RL). They diverge only in who acts and why. Everything below the driver — the action grammar, the tool schema, the observation text, the reward, the run-record — is shared code owned by ARC_Game and imported everywhere. The engine underneath is one Unity build, reached two ways.

02 — The interfaces

The shared contract: six modules, one home

These are the seams between wings. Owning them in one place is the whole point of the unification — change the schema once and it flows to officer, benchmark, and trainer. The Verlog fork already imports ARC_Game live via ARC_GAME_PATH, so it consumes these the same way it already consumes parse_commands.

03 — Who works on what

How collaborators plug into each wing

Different people extend different wings, and each has a self-serve entry point that never requires touching the core. The unified contract means a prompt or tool authored for one wing means the same thing in the others.

Live wing

Trusted lab collaborators · remote agents

  • Upload config bundles (prompts, tool selection) with the cora-bundle CLI → POST /bundles
  • Mint their own API keys for experiment cohorts
  • Add tools & hooks as cora_ext plugins, hot-reloaded
  • Pull their cohort's data back via /my/sessions

Benchmark wing

Prompt & evaluation researchers

  • Author declarative prompt packs (prompts/*.json)
  • Run run_benchmark.sh --prompt-pack against headless Unity
  • Get comparable numbers + full transcripts out
  • Swap prompt → measure, no core changes

RL wing

RL / ML engineers

  • Edit sbatch + configs in the Verlog fork
  • Submit PPO runs on the cluster (tool-call arm)
  • Consume the shared contract via ARC_GAME_PATH
  • Produce checkpoints that redeploy as live officers

04 — The live experience

How a participant plays the GUI/live version

A study participant is the Director. They open the WebGL game in a browser; LLM officers connect through the router and advise them each round. The Director stays in control — every officer suggestion is a proposal the human accepts, edits, or overrides, and the Director can also act directly. Both kinds of action are captured, tagged by who did it.

The provenance flag matters downstream: a Director's direct action and an officer's tool-call land in the same run-record schema, distinguished only by is_human — which is exactly what lets live human play become off-policy data for training.

05 — The closing loop

Where run-data goes — and how the wings feed each other

Every wing appends the same JSONL run-records at the edge (cheap, inspectable, wherever it runs). An aggregation step converts them to parquet for training. That one buffer mixes on-policy RL rollouts, off-policy frontier benchmark runs, and off-policy live-human play — and the model it trains redeploys back into all three wings. That is the research payoff: benchmark and live-human data become fuel for off-policy PPO.

Honest constraint carried in the schema: frontier and human records have no token log-probs, so behavior_logprobs is nullable and messages+raw_response are mandatory — keeping the recompute-under-policy path open without a re-capture, even though we start with the current true-IS setup.
